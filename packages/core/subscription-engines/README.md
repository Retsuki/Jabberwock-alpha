# Subscription engines

Current user images are loaded through the attachment store, which verifies each durable reference and its bytes before native submission. Text and images retain their accepted order; image-only input is supported. Claude receives base64 image blocks and Codex receives inline image data URLs. Resumed turns submit only new input. Provider-switch history sharing remains text-only and does not reload past images; image payloads are never copied into bootstrap records. File attachments remain unsupported and fail explicitly. Cancellation or an unreadable image stops submission.

Jabberwock main-chat execution through the official Codex app-server and Claude Agent SDK. Native tools execute once in the selected project's directory. Harness receives text streams and durable `engine/activity` facts, never executable tool-call chunks.

The `agentEngines` service exposes `codex-subscription` and `claude-subscription`. Both offer the native `default` model. API credentials and provider-routing environment overrides are removed, Codex selects the OpenAI provider and ChatGPT login, and Claude requires first-party claude.ai authentication. Missing or API-billed authentication fails; no API-key fallback exists.

Ordinary Claude and Codex turns collect additional Host tools through the reversible `subscription-engines/host-tools` waterfall. Providers bind each capability to the current Agent and enforce their own authorization. Claude uses SDK MCP tools; Codex uses the bundled app-server experimental dynamic-tool protocol. Catalogs, arguments and results are recorded in the owning Session. Codex validates each call against the live catalog and starts a new native thread when declarations change, retaining the existing history-sharing check. Dedicated conversation-only and Worker routes remain isolated.

Native conversation identities are stored in `engine/session` with the owning Harness Session id. Fork-inherited identities are ignored. Starting a new provider conversation with existing history asks the user to approve sharing previous user and assistant text with the named destination; refusal stops the turn. The exact authorized bootstrap text is recorded in `engine/bootstrap`. Native tools requiring approval use the scoped human-question service; absent answerers deny approval. Claude does not load project or user SDK settings, and starts in default permission mode until explicitly changed.

Configure `codexCommand` to override the bundled official executable and `claudeCommand` to select an installed official Claude CLI. `statusTimeoutMs` and `loginTimeoutMs` bound authentication operations, and `modelListTimeoutMs` (default 8000, minimum 1000) bounds the wait for the Claude SDK model catalog. Credentials remain owned by the official CLIs. Authentication status contains no credential values.

This initial integration accepts text messages only. Attachments fail explicitly. Native tool summaries are durable activity events; dedicated activity cards are a separate consumer.

Codex model choices come from the official `model/list` catalog. The `default` alias resolves to its advertised default at run time, and every turn explicitly selects that model instead of inheriting the user's CLI model setting. Models absent from the catalog fail without fallback. Failed turns expose the provider's error message without exposing the response body or credentials.

Native usage is recorded as replacement `engine/usage` snapshots. Codex reports current context from the last request and cumulative token counters with cached input separated from uncached input; it supplies no invented category breakdown. Claude uses automatic context reports or `getContextUsage({ detail: 'summary' })` local estimates, plus native result token counters. Summary collection does not call the per-category token-count API. Unavailable metrics do not fail successful turns.

The owner-only `subscriptionQuota` service reads account-wide subscription windows independently of Session context. `read({ engine })` and `refresh({ engine })` issue fresh, deadline-bound official control queries; simultaneous reads share an in-flight request, and authentication changes cancel its previous generation. Claude uses experimental structured SDK usage with `skipBehaviors: true`; Codex uses `account/rateLimits/read`, classifying reported window durations rather than assuming a five-hour primary window. Percentages and reset times remain nullable; unsupported, disconnected or failed reads return unavailable without inference, transcript inspection, credential values or Session writes. Account limits cover the account's usage outside Jabberwock as reported by the provider.

Each Claude turn opens a fresh SDK query, whose native counters restart on resume. A resumed Harness session captures its previous Claude token snapshot once, then adds that fixed base to the query's latest cumulative counters; repeated results replace that query contribution. Context-only reports retain the latest token snapshot. Codex's resumed native counters already include previous turns, so no base is added.

Permission presets are stored independently per engine in `engine/permission` and captured at turn start. Codex offers user approval in a workspace sandbox, native `auto_review` in that sandbox, or explicit full access; both thread setup and each turn receive the selected native settings. Claude offers `default`, `acceptEdits`, `plan`, and explicit `bypassPermissions`; the last also sets the SDK's required dangerous-permission flag. Existing human approval callbacks remain in place. Selection changes apply on the next turn, including resumed native conversations; unsupported stored values stop execution. Forked conversations start with safe defaults instead of inheriting parent permissions.

The main-chat Claude group lists `Claude default` plus the models returned by the authenticated SDK `supportedModels()` request, using the same discovery as `claude-conversation` under the `modelListTimeoutMs` deadline. When the account is not a first-party claude.ai subscription, or the CLI, the SDK request or the deadline fails, the group lists only `Claude default` and logs one warning, so the group never disappears. A successful list is cached and concurrent callers share one query; failures are never cached, so the next listing retries. The cache is cleared when `connect('claude')` starts and when `connections()` reports Claude as anything other than `connected`.

The Models subscription cards expose separate `historySharing.claude` and `historySharing.codex` profile settings. Both default to `ask`; an explicit `allow` selection permits text-history bootstrap for new conversations on this installation as well as the current conversation. Settings use the existing volatile profile configuration and persist across restart. Returning to `ask` restores ordinary conversation-level confirmation; a separately granted conversation-level always permission remains valid. Current-input images are unchanged, and historical images, tools and credential files are not added to bootstrap. DeepSeek routes are not covered by these settings. Provider-policy bootstrap is recorded as `history-sharing-policy` activity and does not grant permanent conversation consent. Provider scope refers to Claude/Anthropic or Codex/OpenAI, including another subscription account on the same provider.

`EngineRunRequest.responseSchema` requests native JSON-schema output only on `claude-conversation`. The caller logs that same schema in its task context. The SDK receives `outputFormat`, and only validated `result.structured_output` becomes response text; missing, invalid or failed structured output rejects without falling back to prose. The exact SDK-internal `StructuredOutput` name is accepted only while a schema is requested, and its permission-hook input must validate against that schema. Built-in, MCP, agent, skill and plugin access remains disabled. Native main-chat and host-tools routes reject this schema option; ordinary requests without it keep their existing final-text behavior.

The internal `claude-conversation` route is absent from the main-chat catalog. It uses the same subscription authentication with all built-in tools, MCP, skills, agent definitions and plugins disabled, and denies native tool requests. Without a response schema, SDK initialization advertising tools fails before consuming assistant output; the schema-specific internal output carrier is the only exception. Conversation-only output is published from the successful SDK final result; interrupted or retried partial text cannot be concatenated into the completed response. Ordinary Claude permission presets are unchanged.

The lookup-only `claude-host-tools` route requires explicit `EngineRunRequest.hostTools`. It converts object JSON schemas to typed in-process MCP tools while keeping native tools, agents, skills and plugins disabled. Hooks and initialization reject capabilities outside that request's tool set. The owning service enforces operation policy; model-visible tool arguments and results are flushed into Session activity records. Streaming input remains open until the native result to keep the SDK MCP transport alive.

`register()` adds lookup-only internal engines without changing the main-chat model catalog. Built-in and registered identities cannot be replaced, including `claude-conversation`. The registering plugin owns the returned disposer; disposal removes only its registration, and service unload clears all internal registrations.

The lookup-only `claude-conversation` engine discovers model choices through the authenticated SDK `supportedModels()` control request, without submitting a user prompt. Discovery disables tools and external capability sources, uses `statusTimeoutMs`, and closes its managed process on success, failure, cancellation, or service unload. `default` remains an explicit choice; catalog failures do not produce a synthetic model list. Codex is unavailable for conversation-only consumers because the installed App Server protocol does not provide a verified all-tools-disabled mode.

History sharing asks separately from native tool approval: allow once, always allow in this conversation, or deny. Always-allow consent is replayed from `engine/activity` history-sharing decisions through a host-only projection and applies only to the exact Session identity and destination provider. Forked Sessions and other providers require a new answer. Refusal or cancellation stops transcript bootstrap; native tool approvals remain independent.
