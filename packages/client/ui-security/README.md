<a id="browser-state"></a>
## Browser state

The legacy `jabberwock.security.v1` localStorage record contains versioned projects, registered targets and diagnostic drafts. Legacy projects and drafts remain stored without being assigned or copied into an existing Workspace. The project Assets screen does not read or write these records; the prototype's `artex-state-v1` record is also never read, modified or deleted.

The [security subsystem reference](../../../docs/subsystems/security.md) owns the generated Host API listing. `SecurityRecords` is the atomic Workspace aggregate containing its branded Workspace identity, revision, companies, assets and task drafts. The `security-records/changed` event carries the committed aggregate only after its storage write succeeds. The Host owns company scopes, typed assets and task drafts through `securityRecords.read/save` and the `jabberwock_security` storage domain. Desktop storage uses the configured existing provider. Successful saves await durable acknowledgement; stale revisions require a reload, and failed writes retain the last confirmed snapshot. Empty Workspaces receive no sample seed. Asset-scope changes neither discover assets nor alter actual access controls.

Task overview editing stores optional goal, operation-constraint and scope-rule rows with the task draft. Rows support in-place editing, empty drafts and deletion through the existing 500 ms autosave queue, with flush on blur/navigation. Missing arrays in older records display as empty; the domain remains version 1. These saved intentions do not enforce runtime permissions. Optional fields have no schema defaults: virtual starter rows do not write data until edited.

Security task conversations, Planner attempts, Worker investigations and Worker discussions stay in the task Sessions view. The security plugin registers a reversible sidebar visibility rule for its reserved generated Session identities, including older histories. Ordinary unnamed chats remain visible; no Session is deleted or archived by this rule.

<a id="screens"></a>
## Screens

Each real Workspace in the grouped sidebar has one Security entry. Its page provides Assets, Tasks and Supply-chain tabs. Its selection opens that Workspace's main security panel; Workspace renames update the header. Virtual folders, ungrouped Sessions, flat lists and search results have no invented Workspace navigation. The previous independent project picker is no longer part of this route. Project Assets provides seven category views: companies, root domains, IPs, subdomains, applications, services and endpoints. Company scope dialogs replace or append domain, IP and CIDR targets. Company and asset mutations are saved per Workspace; deleting assets removes their task references. New task creation requires a name and at least one registered asset, saves an unexecuted draft with empty description/objective, and opens the Main Agent in Sessions. The create button states that the selected task context is sent to Claude to begin guided setup. Existing tasks open without starting inference. Drafts retain names, descriptions, objectives and selected asset IDs; pinning, archiving and deletion are durable mutations. Category, concurrency and execution controls are unavailable. Task details provide sessions, overview, exploration, timeline, findings, retests, assets, coverage, approvals and report tabs. Saved tasks render timeline and exploration from persisted activity; preview tasks and asset coverage retain isolated sample data. Preview approval and retest controls never execute requests; saved-task retests use the dedicated findings service. Report copying writes the displayed sample as Markdown to the clipboard.

The plugin registers Japanese as an optional language with English fallback. Existing language selection is preserved. English, Chinese and Japanese dictionaries own UI chrome; migrated sample content retains its original language. Select Settings → General → Language → 日本語 to use the Japanese asset, task, conversation and investigation-plan controls.

Task IDs and detail controls open a separate detail view with a fixed title and tab header. The overview provides goal, operation-constraint, asset-rule, coverage, token-usage and task-status cards. Saved task metadata remains separate from demonstration panels; these panels do not provide execution results or durable detail edits. Legacy browser records remain separate from Host storage.

Saved task Sessions render the durable main-Agent conversation and an independently selected Planner proposal. The Main Agent header reads available subscription engines and models from `securityConversations.catalog` and persists task-local choices through `securityConversations.select`. Saved choices apply to the next message without replacing the Session or composer draft; controls are disabled during a running turn or a pending change. Failed requests retain the previous display and expose a retry action. Codex remains disabled because its native protocol does not enforce conversation-only permissions. Conversation entries are indented below their role headings, with spacing between role groups and existing outline icons identifying each role. The Planner panel shows recorded attempt states, timestamps, snapshots and pending investigations, with refresh and cancellation controls. It does not display private reasoning or invent Worker dispatches or results. Plan creation is requested in conversation, without a separate creation button. Legacy browser-only previews retain local sample sessions; they do not send messages to an AI. Attachments remain disabled.

The main-Agent header toggles an initially visible, read-only setup checklist with an Open overview shortcut to the same task. Saved task facts determine goal/completion, scope, permission, operation restrictions and execution limits. The Main Agent asks one missing question at a time; valid settings from completed replies are saved automatically through revision checking before the next question. No routine confirmation button interrupts the conversation. Failed saves or follow-up admission expose a retry action; conflicting direct edits require revisiting the settings in conversation instead of overwriting them. Record revision changes refresh the overview while retaining unsaved manual edits. Scope and permission confirmations are invalidated by material scope edits; goal edits require a new completion condition. The overview retains the saved completion condition and limits. All five checks are required for a conversation-driven Planner handoff, including legacy tasks; complete setup permits planning, not target execution.

Setup instructions include the full response schema, including each scope-rule field. One complete JSON code fence is accepted with the same strict field validation; a refusal reply does not imply an execution action. A completed response with malformed JSON or schema-invalid fields gets one format-only correction attempt on the same engine/model; the original task context and owner action remain authoritative. The correction input and prior raw response are recorded in the Session, and usage from both attempts is counted. Provider failures, non-stop completion, cancellation, storage failures and post-parse task/model authorization failures are not retried. Complete free-text output, including a refusal explanation, can receive this format-only correction; no refusal-meaning inference or restriction bypass is performed. Two invalid responses leave task settings unchanged and show a localized resend message.

<a id="role-models-and-one-bounded-worker"></a>
## Role models and one bounded Worker

Overview stores Main Agent choices in `task.agentModels` and offers automatic or fixed selection for Planner and Worker through `task.agentModelModes`. In automatic mode, the Main Agent selects an advertised Planner model with a concise reason when requesting planning, and Planner selects an advertised Worker model and reason for each investigation item. The Host validates actual catalog IDs; `default` is not an automatic decision. Fixed owner preferences take priority. Clear conversational preferences save through the setup journal; unsupported providers do not become invented saved choices. Settings affect only new invocations, whose actual choice and reason are retained. Missing modes interpret legacy explicit models as fixed and missing/default selections as automatic. Older plans remain readable; automatic Worker execution requires regenerating plans that lack item model decisions. The Main Agent header edits its existing shared choice; unsupported tool-free providers remain unavailable.

New investigation starts use the task’s saved registered assets and scope rules; neither the execution form nor an individual item requires an owner-entered URL. Planner assigns an investigation and the Worker chooses successive checked tools. `securityWorkers.start/read/cancel` owns durable runs in `jabberwock_security_workers`, independently of task drafts and Planner items. Tools cover HTTP requests, retained evidence windows and private scratch files. Query parameters are supported; non-read HTTP methods and credential-bearing requests require explicit saved permission and per-operation approval. Redirects are observed, not followed automatically; each destination requires another checked request. Proxy routes, non-public addresses, denied scope, unsupported natural-language constraints and stale plans reject. Public DNS is rechecked and pinned for every request. Observations and model-visible tool activity are retained before the next model step. Findings retain references to their supporting observations; failures preserve acquired evidence. Historical single-GET runs remain readable.

Configuration fields `workerTimeoutMs` (15000), `workerMaxResponseBytes` (4194304), `workerModelResponseBytes` (65536) and `workerModelTimeoutMs` (180000) are captured for each new run. Response capture and per-model text budgets are independent; requests, tool calls and model steps also have finite budgets. These limits do not compile arbitrary free-form stop conditions. Claude subscription Workers expose only explicitly registered in-process MCP tools; native tools, subagents, skills and plugins remain disabled. DeepSeek account/API loops use the same explicit capabilities, but real-model verification is pending. Codex Workers remain unsupported. Dispatch uses a rolling pool; completed Workers release their slots after cleanup.

The offline command tool is macOS-only and requires the managed subprocess service. A deny-default Seatbelt profile blocks networking, unrelated project/home reads and process forks. Commands are single-process: pipelines, background jobs and subprocess-based scripts are unsupported. Other hosts refuse execution rather than falling back to an unconfined process. HTTP traffic always uses the checked HTTP tool.

<a id="planner-feedback-execution"></a>
## Planner feedback execution

The Main Agent starts an owner-delegated investigation from saved assets and scope rules; Planner displays its activity and stop controls. `securityExecution` captures `targetMode: asset-scope`, the task and asset snapshot, rounds, child identities and decisions independently of editable task records. Planner assigns scoped investigations, receives saved multi-step Worker observations and chooses continue, complete or needs-input. Each new operation is validated against the captured asset scope and deny-first rules, including public-address checks at request time. Legacy executions without this mode retain their exact-target restrictions and remain readable. Cancellation settles owned children, changed operational settings stop dispatch and restart never automatically resumes requests. The panel displays progress and retained decisions. This bounded tool-using workflow does not yet match the full ARTEX toolset. Saved reports describe its actual observations and gaps.

The free-form `task.setup.limits` text records the owner’s requested limits; it does not configure execution budgets. `security_control.read.executionLimits` exposes the Host limits for new investigations. Skills compare the saved request with these effective limits before starting; a mismatch requires clarification instead of assuming the text is enforced. Resumed runs retain their saved execution snapshot limits, exposed as `executions[row].limits`; start/resume results also include each run’s snapshot limits. Use `executionLimits` only for a new investigation, and the selected run’s limits for resume.

`executionMaxConcurrentWorkers` configures 1–10 concurrent Workers (default 3). New executions capture the limit; old snapshots without it remain sequential. Available slots take pending investigations without a batch barrier. Saved dispatch reservations partition the shared HTTP budget, and unused quota returns after Worker cleanup. Manual starts cannot bypass an active coordinator. Individual messages, approvals and cancellation address a Worker run; task cancellation fences queued admissions and awaits all children. A settled Worker triggers one Planner review while other Workers continue. New dispatch pauses during review; later results wait for the next review. Durable review identities distinguish captured results from ongoing progress and record decision application. Only explicitly named ongoing Workers are stopped; a replacement pending queue does not cancel them. Explicit resume applies saved ready decisions once, and restart remains passive.

<a id="shared-exploration"></a>
## Shared exploration

Planner and Workers share goals, investigations, HTTP observations, evidence-linked facts, findings and unverified hints through `securityExploration`. Original records retain their owners; only annotations and supporting relationships use the new task domain. Worker `read_exploration` reads shared knowledge and `publish_fact` records a claim with an exact quotation from that Worker's retained observations. Planner captures logged shared input and can return investigation links, hints and evidence-linked goal assessments. Assessments never change task completion or finding triage. Ready annotations are applied idempotently before dispatch, and application failures block dependent work. Task-scoped serialized writes preserve concurrent results; stale settings invalidate goal assessments without deleting evidence. `explorationModelBytes` bounds complete serialized model reads (default 65536, range 1024–1048576); truncated views report omitted records, and Workers can request specific node IDs. Owner graph reads retain the full projection. These inputs consume model tokens and use existing tool-call limits; no new target permissions are introduced.

<a id="main-chat-control"></a>
## Main-chat control

An ordinary owner chat registered to exactly one Workspace receives `security_control`. Native Claude uses its in-process host-tool bridge; the ordinary Harness route exposes the same command to DeepSeek. Codex has no compatible host-tool bridge and cannot perform these controls. Dedicated security Sessions, delegated agents and non-owner callers do not receive owner control authority. Workspace identity comes from the live calling Session, never from model arguments.

The owner can ask “List the security tasks,” “Create a task using this registered asset,” “Change this task's goal,” “Start this task's investigation,” “Stop this task,” or “Open this task's findings.” The tool lists assets and task summaries, reads saved configuration and progress, creates or updates task drafts, delegates start/resume/stop to existing execution owners, and sends additional instructions to a named existing Worker. It does not send messages directly to the Planner. Explicit `open` results provide a task-screen button; clicking it revalidates the task and flushes pending edits before navigating. Navigation failures remain visible.

Mutations use the current saved revision and reject conflicting edits. Creation uses a stable request identity scoped to the calling Session; retries preserve it. Setup confirmations require an exact quotation from the current owner message rather than a guessed permission. Start and resume require an explicit current-owner investigation request plus existing checklist and execution checks. Stop awaits owned execution, planning and Worker cancellation. Accepted work is not completed work. Tool inputs and results remain in the invoking Session's normal history; existing provider consent still applies.

The `plan` operation delegates to the existing planning service with the current revision and stable retry identity. It returns the saved planning attempt without dispatching Workers or accessing targets. Planning retains the setup checklist, model selection and active-conversation admission checks. Read results include saved Planner and Worker failure reasons within the same output limit.

`controlModelBytes` bounds the complete serialized tool result, including navigation coordinates (default 65536, range 1024–1048576). Oversized results disclose truncation. List pagination and explicit task reads provide narrower results; omitted content must not be inferred. No new persistence domain or automatic execution on restart is introduced. The [approved design](../../../docs/adr/0014-main-chat-security-control.md) records the common operation ownership.

<a id="conversational-investigation-handoff"></a>
## Conversational investigation handoff

The Main Agent distinguishes planning-only requests from an explicit current-owner request to delegate investigation. A completed structured investigation action saves task edits first, validates readiness and the advertised Planner choice, and starts the task-owned coordinator with a stable request identity. The coordinator owns initial planning and subsequent Worker feedback; an older plan without an automatic model decision is not silently reused. Reading a task or receiving an automatic setup continuation never starts target access.

Sessions show Main Agent, Planner, system audit and actual individual Worker entries. Worker rows retain their run identity and status as new runs appear; selecting one opens its run-owned conversation and expandable execution evidence. Planner displays compact, expandable round activity and decisions. The Main Agent’s Start investigation button sends the same explicit delegation message as chat without changing an unsent draft; progress and stop remain visible in Planner. Model-private reasoning and fictitious tool activity are not displayed.

Supported operation descriptions are checked before dispatch and again before transport against each requested method and credential use. Explicit HTTP observation, banner inspection and service/version observation permissions do not enable port scanning or exploit tools. Read-only rules reject write requests; authentication and non-read operations additionally require saved permission and owner approval. Exploit, brute-force and stress-test capabilities are not introduced by these permissions. HTTPS-only and GET prohibitions restrict actual requests; unknown or ambiguous constraints stop execution and identify the unsupported text. These checks constrain Worker requests, not the behavior of the remote server. Confirmed operation settings must match the saved constraints; older tasks without confirmation metadata remain readable.

DeepSeek account and API models are available to all three roles through the existing provider catalogs. The routes retain separate identities and never fall back to one another or to a different model. Main-Agent discussion stays tool-free; dedicated Worker routes expose only run-owned tools. Actual DeepSeek model execution remains unverified. Historical discussion is shared only after consent for the exact task Session and DeepSeek destination; always-allow consent is stored with that task conversation. Model choices and automatic decisions use the same saved selection controls as Claude. Unavailable providers/models remain unavailable, and old Claude/Codex records keep their existing interpretation.

<a id="worker-conversation"></a>
## Worker conversation

An individual Worker opens a run-owned conversation with Planner instructions, the actual tool log and HTTP evidence, the Worker report, correlated Planner reviews and owner follow-ups. Ready saved plans contribute their actual review summary only for referenced Worker runs, with stable plan-derived entry identities. Request/evidence details expand within the transcript; private reasoning is excluded. Running and completed views retain saved history after restart, with fixed header/composer and independent message scrolling. Investigation and follow-up activity show animated loading indicators in the Worker list and conversation; reduced-motion preferences disable rotation.

Owner follow-ups use the captured tool-free model to discuss existing evidence, without requesting another URL, restarting HTTP or enabling shell execution. Planner remains responsible for new investigation operations. The Host checks task/run ownership and deduplicates retries. One instruction can queue during the initial run; its analysis waits for that operation to settle. Active or queued follow-ups block another submission. Conversation status does not replace the original execution status; cancelling the selected run also stops its active or queued discussion. Failed, cancelled and interrupted replies remain distinct from completed reports. Older runs without conversation fields remain readable.

<a id="timeline-and-exploration"></a>
## Timeline and exploration

Saved task activity reads existing plans, Workers and executions without inference or target access. Timeline supports search, filters, chronological sorting, actual refresh pause/resume and expandable metadata, related records and payload. Exploration shares the same stable identities and recorded relations; two-finger scrolling pans, trackpad pinching zooms around the pointer, selection highlights connected edges, and the scrollable details panel initially collapses raw payloads. Current goal and asset context do not imply historical creation or achievement; observations and model reports do not imply confirmed vulnerabilities. Failed reads retain the prior view with a visible error.

<a id="findings-and-retests"></a>
## Findings and retests

Findings retain their original evidence and Worker identities when linked as duplicates. Automatic links require identical anonymous read context, asset, method, complete URL, normalized title, severity and proof; unknown or authenticated context remains separate. Owners can link or separate same-asset reports, and explicit separation persists. The list and reports show representatives with expandable related evidence. Retest histories retain their original finding references.

Saved-task findings import only completed Workers' structured reports with quotations from retained HTTP evidence. Original evidence and source identities remain durable while owners manage triage separately. Older narrative summaries do not automatically become findings. A complete leading JSON object or code block may be followed by explanatory prose; only the object supplies structured finding fields. Unused top-level report metadata is ignored, while each finding and its evidence quotations remain strictly validated. The findings tab provides severity, target, time, triage and expandable evidence; the retest tab selects a finding and retains each independent attempt, notes, evidence, conclusion and Session link.

A retest explicitly requests one new anonymous GET of the finding's original URL under the current saved asset scope and operation policy. It uses the selected Worker model, or the original captured model when delegated selection is automatic, and the same bounded public DNS-pinned transport. Unsupported validation remains inconclusive; this does not add authentication, exploit execution or arbitrary tools. Only successful completion with a supported fixed verdict, a normal successful response and quoted normal-function evidence atomically updates triage with the terminal result. Original proof remains unchanged. Cancellation and restart retain interrupted history without resuming traffic.

<a id="response-files-and-reports"></a>
## Response files and reports

New Workers and retests stream bounded responses to task-owned files beneath `DSH_HOME/security-evidence`. The model receives bounded excerpts with byte offsets rather than the whole file; a large response uses beginning, middle and end windows. Reaching the capture cap retains partial evidence without a size-limit failure. Acquisition and analysis completeness remain separate: a fully saved response may still be only partially read. Missing files fail visibly, and old inline evidence remains readable. Partial capture or analysis cannot establish a fixed retest verdict.

The Report tab derives the latest execution's task snapshot, planned operations, actual observations, findings, retests and limitations from saved records without inference or target access. It separates confirmed observations, partial checks, unverified work and unsupported operations. Failed or incomplete checks prevent a broad completion conclusion; zero findings does not establish that the asset has no vulnerabilities. Markdown copy and download use the same data shown on screen. Earlier failed attempts retain their original history.

<a id="worker-browser-login"></a>
## Worker browser login

The Worker section includes Browser login settings before execution. Enter an authorized origin and credentials there; they stay in Host memory, never in task records or model prompts. Clearing settings, changing task authorization or stopping the Host removes them. Browser tools keep one private cookie jar per Worker; credentials are not shared with another task or origin. Login success must be checked from the resulting page. Revoking a saved permission, scope or operation confirmation cancels active Workers and clears their configured browser credentials. Every tool request also checks the current saved authorization, so a missed change notification cannot retain access.

`workerBrowserEnabled` enables browser tools (default true), `workerBrowserHeadless` hides their windows (default false), and `workerBrowserExecutablePath` optionally selects installed Chromium. With no path, the adapter uses Playwright Chromium when installed, otherwise the standard Chrome channel. Missing browsers fail visibly. Navigation, page snapshots, CSS-selector clicks, ordinary field filling and selector-only private login share the existing scope, HTTP quota and operation approvals. Cookies count as authenticated requests; saved GET-only or login-denial constraints are still enforced. Subresources consume the same quota, so ordinary pages may need a larger configured request allowance.

Browser transport records redacted HTTP observations without persisting raw cookies or login values. Raw browser capture retains the configured response cap; the public model excerpt is limited to 1 MiB independently of that cap. Form POST operations may wait for approval in the existing Worker panel. Browser state is discarded on completion, cancellation or restart. Main-document 301/302/303 redirects use fresh checked navigation; 307/308 and subresource redirects are unsupported. Service Workers, WebSockets, extra tabs and downloads are blocked. Cross-origin SSO is unsupported. Additional authentication requires owner intervention; CAPTCHA and hardware authentication are not automated.

<a id="planner-and-worker-token-usage"></a>
## Planner and Worker token usage

Planner and Worker headers show provider-reported input, cache-read and output token counts. Planner adds the latest cumulative values of distinct saved Planner Sessions; a Worker shows only its own Session, including follow-up replies. Hover details include exact counts and cache writes. Unreported measurements appear as an em dash and reported zero remains zero; a missing Session cannot silently become a complete role total. Existing Session projections supply initial reads and live updates, so viewing usage starts no model or diagnostic request and adds no separate meter or durable counter. These counts do not estimate monetary charges.

<a id="asset-coverage"></a>
## Asset coverage

The saved-task Coverage tab projects registered assets, company containment, task scope and actual task-owned HTTP observations into a read-only relationship graph. Its observed/eligible ratio is a rough measure of reach, not diagnostic completion or proof of safety. Plans alone do not count as observations; company and context-only root nodes never enter the denominator. Scope uncertainty and zero eligible assets leave the percentage unknown. Search, filters, folding, pan, pinch zoom and an independently scrolling detail panel expose saved planning, Worker and finding references without contacting targets or models.

<a id="planner-recovery-and-continuation"></a>
## Planner recovery and continuation

Saved Worker results reach Planner review at important findings, failures, HTTP budget exhaustion and batch completion. Review reads authoritative execution budgets and findings; exhausted HTTP budget allows a saved-result review but no further target request. Cancellation, changed settings and elapsed deadlines stop immediately. Unchanged continuation items retain explicit source references, so a shared URL alone cannot complete another investigation objective. Terminal execution summaries are expanded initially so the saved stop reason is visible. Stop guidance uses saved terminal status and exact known system stop messages to distinguish exhausted limits, an explicit Planner input request and interruption; unknown causes are not guessed, and no automatic resume or successful continuation is promised.

`plannerResponseAttempts` bounds the total complete responses for one Planner admission (default 2, range 1–3), within the shared `plannerTimeoutMs` deadline. JSON syntax, structural validation and invalid continuation references request another logged response in the same Session; policy, model, storage, provider, timeout and cancellation failures stop normally. Initial planning and result review each expose one output contract. Continuation identity still requires exact unchanged investigation fields and one unresolved source item; changed investigations must omit continuesItemId. Invalid response fragments are never extracted or combined locally.

The Main Agent header can explicitly resume a failed, cancelled or interrupted execution with `resumeRunId`; a new execution records `resumedFromRunId` and leaves the original history unchanged. Current task revision, assets and operating scope must match, and the original Planner model is retained. Completed or failed Worker observations are reviewed without repeating target access. Interrupted or cancelled work remains unverified. Consumed request and successful-review round budgets carry forward; explicit continuation opens a new elapsed-time window. Restart stays passive. Needs-input requires reviewing task settings and report gaps rather than repeatedly starting the same stopped decision. Optional continuation fields preserve existing saved records.

`workerResponseAttempts` similarly bounds report responses after a captured investigation (default 2, range 1–3). Corrections share the Worker model deadline and retained evidence; the model is instructed not to repeat network requests merely to repair JSON, and any further tool use remains subject to the same run budget and policy. JSON syntax, incomplete code fences and structural validation can be corrected; evidence-quotation violations cannot. Old failed Worker histories remain unchanged. Reports include localized request/round/time-limit stop reasons even when the terminal state is needs-input rather than an error.

<a id="explicit-loopback-test-targets"></a>
## Explicit loopback test targets

`localHttpOrigins` defaults to `[]`. An owner can configure up to eight canonical `http://127.0.0.1:<non-default-port>` origins for local test targets. Startup rejects host aliases, LAN addresses, IPv6, credentials, paths, queries and fragments. The selected asset, exact port, operation restrictions and deny-first task scope still apply. The transport skips DNS only for those exact origins and pins IPv4 loopback, retaining bounded HTTP capture without automatic redirect following; credential use and non-read methods remain subject to the saved permission and approval checks. Planner, Worker, execution and retest admission share this policy; model output cannot change the allowlist.

The test-only `tests/fixtures/vulnerable-lab.ts` exports `startVulnerableLab({ port, fixed })`, returning its origin and async close function. It binds only IPv4 loopback and serves synthetic configuration and user records. Normal mode exposes these records anonymously; fixed mode returns 404 or 401 for the affected routes. It does not load real credentials, contact external services or execute commands. Actual model-driven detection is verified separately from the deterministic fixture and transport tests.


### Executive report view

Saved reports use eight vertically ordered executive sections with themed summary cards, severity and affected-asset bars, prioritized findings, recorded impact/scenarios, remediation priorities and scope qualifications. Figures summarize saved task findings, excluding false positives and duplicates; fixed records remain historical and do not raise active risk. The highest active severity is a prioritization indicator, independent of investigation completeness. No findings does not certify safety. Existing technical Markdown export and expandable evidence retain the complete records. Opening this view does not run models or targets.

<a id="model-experience"></a>
## Model Experience

Saved tasks expose one task-owned Claude conversation through `securityConversations.open/send/cancel`. The service owns the durable task-to-Session mapping; the existing Session projection and follow transport own transcript rendering. Each accepted turn includes a logged task-configuration notice. An explicit Main Agent request starts a separate Planner through `securityPlanning.start/read/cancel` after five setup checks pass and automatic saving settles. Revision checking rejects changed settings; completed-turn request identity prevents duplicate handoff. Ordinary conversation and checklist completion do not silently start planning. Workers use a separate bounded, policy-checked tool executor; unsupported free-form constraints block execution. Ordinary chat Sessions keep their existing routes and permissions.

Security setup passes the exact JSON Schema already recorded in its context notice through `EngineRunRequest.responseSchema` on every attempt. Claude conversation-only requests use native structured output and reject missing or invalid structured results before the unchanged strict proposal parser. Other engines retain their existing text output plus strict setup validation; native structured-output support is not claimed for them. A format correction cannot change owner intent, saved permissions, model selection or the existing retry bound.

The conversation-only engine disables native tools, MCP servers, skills, agents and plugins, denies native tool hooks, and refuses SDK initialization advertising tools other than the schema-specific internal structured-output carrier. Codex conversation-only execution is unavailable. Sending requires saved task edits; overlapping submissions reject, retries reuse the request identity, and cancellation awaits durable settlement. Live Worker model responses require native-account verification; no target is contacted merely by opening task details.

The `jabberwock_security_planning` domain stores immutable task/input snapshots and one independent Session per attempt. Completed proposals accept plain JSON or one complete JSON code fence, with strict field validation. Validated proposals contain only pending, unapproved investigations; unknown asset IDs reject the attempt. Stable request IDs deduplicate submissions, each task admits one active Planner, and cancellation accepted before completion prevents a late ready result. Prior plans survive failed retries. Unfinished attempts become interrupted on restart. The `plannerTimeoutMs` plugin setting bounds planning (default 180000 ms). Planning never invokes target HTTP, shell or Worker execution.

<a id="known-limitations-and-deferred-work"></a>
## Known Limitations and Deferred Work

Workers execute a bounded tool loop with checked HTTP, evidence access and private files. Authentication and non-read requests require saved permission plus approval; redirects require a new checked call. Offline commands are single-process and macOS-only. Codex Workers remain unsupported; actual DeepSeek models are unverified. Private networks remain blocked except exact owner-configured loopback test origins. Reports summarize saved evidence and cannot establish exhaustive vulnerability coverage or independently verified business loss. Main-chat controls share the same task service owners; Codex main-chat control is unavailable.

Repair reports preserve the follow-up run ID as a historical reference, not a navigation link; its result may have been deleted. Current-owner delegation rejects explicit negative requests, including requests declining to start investigation or planning.

## Supply-chain check

The Workspace Security page provides a task-style Supply-chain check list. Its Start action immediately creates a running row and starts a fixed npm/pnpm lockfile advisory check without an LLM. Opening a row embeds its existing ordinary Session conversation and report; saved history is not duplicated. It shows progress, cancellation, package/version findings, dependency scope and an expandable factual report using existing report components. Shared workspace locks retain their actual shared scope. Saved notice messages carry validated run snapshots and explicit history visibility; completed results survive restart without an automatic scan or model turn. Each history row offers View report (the same detail as opening the row) and Delete, after a confirmation. Delete hides one finished run logically through the Workspace owner's `securitySupplyChain.deleteRun`: the run stops appearing in list, read, repair and the shared conversation, and stays hidden after restart. A run restored after restart reopens its Session without a model turn before the deletion is recorded; if that fails, nothing is recorded and Delete can be retried. If the Session log flush fails, the deletion outcome is unknown: the run stays hidden and an error is shown, and repeating Delete acknowledges only after a new flush succeeds. A deleted run's `requestId` cannot start a new check. A running check or repair cannot be deleted; stop it first. The Session log keeps every earlier snapshot as evidence, other runs in the same Session stay, and project manifests, lockfiles and repair recovery files are never touched.

The scanner sends locked package names and versions to the npm registry bulk advisory API. Optional public GitHub advisory lookup sends only public GHSA IDs to its fixed API host, without a token. Source, environment-file contents and credential-file contents are not uploaded. Optional metadata failures remain visible as unknown information. The scanner never installs, updates or fixes dependencies or executes project code. Matching known advisories does not establish code reachability, application exploitability or absence of unknown vulnerabilities; incomplete or failed checks never imply safety.

Individual and bulk repair are separate explicit owner actions on completed checks. Initial repair supports standalone projects with public direct semver dependencies; shared/workspace, private, override and unsupported dependency definitions require manual handling. Older scans without a definition fingerprint require a fresh check. The Host stages fixed npm/pnpm lock-only commands outside the project, with scripts/hooks disabled and package-manager configuration/environment isolated. It refreshes all advisory comparisons, validates selected candidate versions and checks original manifest/lock hashes before applying backed-up definition files and rescanning. No arbitrary command or caller-supplied version is accepted.

Repair records preserve selected changes, all locked-graph version-change summaries and per-file hashes. They do not present a complete source-file diff. Original bytes and per-file application progress are retained in an owner-only recovery directory. Cancellation, conflicting edits or partial application remain explicit; automatic rollback never overwrites newer owner edits. Repair updates package.json and the lockfile only: node_modules installation, application build and functional health checks remain not run. Advisory clearance is not application-health success. Running repairs restored after restart are interrupted and never replayed automatically.

## Product security skills

The application bundles `security-task`, `security-plan`, `security-investigate`, `security-status` and `security-report` in its package assets. Its Host provider registers them with the shared skill registry independently of the selected Workspace or project-local `.agents` folders. The existing `skill` loader publishes descriptions and loads the selected workflow together with one shared rules resource. Planning uses the plan-only `security_control` operation; it does not dispatch Workers. Native engine discovery and tool availability follow the subscription engine integration.
