# 工作区供应链检查规格

[English](supply-chain-check-spec.md) | 中文

> B 架构已获批准，固定扫描器及报告 UI 已实现。验证记录区分已执行检查和剩余检查。工作区所有者可将锁定的 JavaScript 依赖与公开安全公告比对，并在持久化对话中查看结果。无需大模型、安装依赖或自动修复。包名与版本会发送至 npm 注册表；不包含源码、环境文件或凭据文件正文。不提议新增数据库。

## 用户流程

1. 点击工作区 Security 侧边栏中的 `サプライチェーンチェック`（Supply-chain check）。
2. 打开属于该工作区的专用普通对话，并自动启动固定扫描器。运行期间重复点击只重新打开该对话，不再次扫描。
3. 显示进度阶段：识别锁文件、查询安全公告、整理结果。所有者可取消活动运行。
4. 将进度、结果和事实发现保存为 Session 事件。应用重启后可阅读对话；扫描不会自动恢复或重启。
5. 锁文件缺失或不受支持、注册表不可用、取消导致覆盖不完整时，显示未完成／错误／已取消状态与已检查范围。不得将未完成的零发现结果等同于安全。

## 覆盖与结果

初始范围是 JavaScript／TypeScript 应用的 npm 和 pnpm 锁文件，包括 Next.js。对于工作区共享锁文件，结果说明根锁文件及实际共享依赖范围，不声称具备包级精度。区分直接／间接依赖及生产／开发分类；无法可靠拆分时，保留共享或未知分类。

结果包含事实 Markdown 和结构化行：包、已安装版本、修复版本或明确无修复信息、公告严重程度、可用的 GHSA／CVE 标识与来源链接、公告公开／更新日期、一般影响及其依据、项目影响评估（已确认、条件成立时或未验证）、直接／间接关系及生产／开发分类。不得将公告公开／更新日期呈现为项目发现日期。汇总数量说明计数单位和检查范围。公告未提供修复信息与已确认不存在修复应区分。

此检查匹配已公开的依赖安全公告。不证明代码可达性、可利用性或不存在未知脆弱性。完整扫描零公告只代表已检查数据未匹配，不代表应用安全。

## 报告展示

对话展示已保存结果与发现表格。所有者可展开一行或打开其报告。复用现有 ExecutiveReport 展示及共享报告组件，使严重程度、证据、影响与限制符合产品 UI。报告区分注册表事实、公告一般影响与项目具体观察。仅有静态导入不能证明可达性或项目影响已确认。

## Host 执行与共享

Host 将已注册工作区身份解析为可信目录。调用方不能提供任意 `cwd`。扫描器使用固定、无 shell 的操作，限制耗时、网络响应和显示输出。不得安装包、运行项目脚本或应用修复／更新。将锁文件中的包名和版本发送至 npm 注册表比对公告，不提交源码、环境文件正文或凭据文件正文。检查对话与报告说明发送目标及数据范围。

npm 注册表审计响应提供主要事实。可选的公开 GitHub advisory API 查询可补充已知 GHSA 标识、日期和影响描述：请求使用固定 GitHub API 主机，仅发送公开 GHSA ID，无需 token。补充信息缺失或获取失败保持未知，不得隐藏主要结果。不得向任一服务提交源码、环境或机密文件正文。本功能不执行载荷、利用或攻击应用。

## 集成

`packages/client/ui-security/src/client/WorkspaceSecurity.tsx` 负责入口。现有 session-controller `commands.create` 使用 `workspaceId` 创建对话；`UiWorkspace.openSession` 打开它。`uiConversation.events.register` 渲染扫描事件。固定扫描器负责方使用现有 Session 生命周期与 `ctx.jobs.start`，并通过 jobs 服务等待 job，完成时不唤醒对话模型。Job 是临时的。进度和结果作为既有 `user/message` 提示保存，携带 `source.kind=security-supply-chain`、`form=notice`、所有者身份及已验证的类型化运行快照。来源类型允许可选 `visibleInHistory?: true`；生成方明确写入 true，使普通侧边栏保留此对话，而不显示其他内部提示。停止或卸载运行会取消工作，注册表失败仍属于未完成／错误结果。

提议命名空间为 `securitySupplyChain`；实现可在不改变约定的情况下细化名称。操作接受身份及幂等键，不接受文件系统路径：

```json
{"operation":"start","workspaceId":"workspace-1","requestId":"request-1"}
{"accepted":true,"runId":"run-1","sessionId":"session-1"}
{"operation":"read","workspaceId":"workspace-1","runId":"run-1"}
{"operation":"cancel","workspaceId":"workspace-1","runId":"run-1"}
```

现有 Workspace／Gateway 访问检查适用于创建、读取和取消。重复请求返回已有运行／对话身份。同一工作区的并发启动请求不得创建两个活动运行。

## 已批准架构

A 让聊天模型执行检查，扫描行为依赖模型工具和指令。B 提议专门的固定扫描器负责方，连接现有 Session、jobs 和对话事件渲染；无需大模型，也不重建聊天持久化。C 替换执行与对话基础设施，使变更超出本检查。B 已获批准。本规格记录约定行为；实现与验证由[实施计划](supply-chain-check-implementation-plan.zh.md)跟踪。

## 验收条件

测试覆盖 npm／pnpm 锁文件、共享工作区范围、直接／间接与开发／生产报告、零匹配、有／无修复信息公告、锁文件缺失／不支持、网络失败、超时、取消和重复／并发点击。实际 UI 验证需确认专用对话、可见进度、重启后结果保留且不自动重跑。外部注册表测试必须使用已披露的包名／版本数据；不得上传源码或机密文件。

## 已批准的导航与修复扩展

B 已批准并实现；验证文档记录已执行检查与剩余限制。现有扫描器、已保存对话和报告仍为当前行为。单个 Security 侧边栏入口将打开带 Assets、Tasks 和 Supply-chain 顶部标签的 SecurityPage。Supply-chain 标签展示任务式检查列表，右上角提供开始按钮；启动时立即增加运行中行。打开一行将嵌入其现有 Session 对话与报告，不创建第二份历史。

单项和批量修复操作将更新依赖，然后进行新扫描，保留前后结果。初始修复仅支持独立项目的公开直接依赖。修复负责方在隔离的包管理器环境／配置中暂存固定 npm／pnpm 仅锁文件操作，禁用安装钩子／脚本。重新检查全部公告，验证原始 manifest／锁文件哈希，然后备份并应用 manifest 与锁文件，启动新扫描。具体实现必须保留这些检查，并报告拒绝或失败步骤。公告数量减少不证明应用仍正常；未执行的应用检查必须保持未验证，不得显示成功。只读扫描仍保证不安装／不更新；仅明确的独立修复操作可修改 manifest 与锁文件。不刷新 node_modules，也不验证应用健康。

A 在聊天路径中增加列表和修复行为。B 复用扫描器服务与现有历史，增加列表／读取操作，并将依赖修复置于独立负责方；B 已批准。C 重建扫描器、历史和导航基础设施，范围最大。修复需要所有者明确执行单项或批量操作，且独立于启动只读扫描。[架构决定](../../adr/0016-supply-chain-navigation-repair.zh.md)记录职责划分。
